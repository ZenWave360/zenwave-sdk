# Final synthesis: ZDL listeners and AsyncAPI consumer generation

The design is based on four implementation decisions, plus the module-ownership rules and the
cross-module `@listener` contract in sections 5–7.

## 0. Module ownership (hard rules)

- **`plugins/asyncapi-spring-cloud-streams3` is FROZEN.** It exists as historical reference only.
  It must receive zero changes and must not be used or extended by any new generation feature.
- **`plugins/asyncapi-ops` does not generate application adapters.** It remains focused on
  operational infrastructure derived from AsyncAPI.
- `plugins/asyncapi-generator` owns transport listeners, consumer/producer interfaces, typed
  headers, and payload DTO generation. Its Maven execution selects JSON Schema or Avro DTO
  generation internally.
- `plugins/backend-application-default` owns internal `@listener` classes and concrete inbound
  adapter implementations. It reads referenced AsyncAPI models to plan implementations, but never
  calls `asyncapi-generator`; that plugin must be configured as a separate Maven execution, just
  like the existing event-publishing integration.

## 1. Shared URI-capable resource loader

Implement `SpecResourceLoader` by extracting the proven behavior from `DefaultYamlParser`. It must support:

- `classpath:` resources
- local files
- HTTP/HTTPS URLs
- authentication configuration
- correct relative `$ref` base resolution

Every `apis {}` entry is loaded and parsed independently into its own referenced API model. Referenced ZDL or AsyncAPI documents are never concatenated with the primary model. The existing multiple-primary-`zdlFiles` behavior remains unchanged for now.

## 2. Plain mapper contract plus generated-once MapStruct implementation

For mappings classified as `GENERATED`, generate a plain contract interface on every generation:

```java
public interface PaymentsProcessingConsumerMapper {
    Long confirmOrderId(PaymentAuthorized event);
}
```

Also generate a developer-owned MapStruct extension once:

```java
@Mapper(componentModel = "spring")
public interface PaymentsProcessingConsumerMapStructMapper
        extends PaymentsProcessingConsumerMapper {
}
```

The adapter depends on the plain contract interface; the MapStruct extension supplies the Spring bean and customization point.

This scaffold is generated only when the planner can prove that the signatures are safely MapStruct-compatible. For `CUSTOM_REQUIRED` shapes—multiple consumable messages, ambiguous unions, unsupported parameters, or uncertain conversions—no speculative mapper method is emitted. The adapter instead contains a compiling, clearly marked customization body.

This preserves both requirements:

- initial generated output always compiles;
- customization errors appear at compile time in developer-owned code.

## 3. Different adapter ownership strategies

Backend AsyncAPI adapter implementations use the base/extension pattern because their generated
interfaces can change externally:

```text
GeneratedPaymentsAdapterBase    regenerated
PaymentsAdapter                 generated once, developer-owned @Component
```

The base owns regenerated SDK-facing methods and common plumbing. The extension owns custom bodies and mapping decisions. Contract drift therefore becomes visible without overwriting developer code.
For imperative consumers, both layers retain `asyncapi-generator`'s two-argument contract:
`(raw event, typed headers)`. Safe raw-event-to-local-input mapping happens inside the generated-once
extension immediately before invoking the local service.

Internal Spring Modulith listeners remain a single generated-once class:

```text
OrderEventsListener             generated once, skipOverwrite=true
```

There is no external SDK interface driving internal listeners, so the additional base class would not provide enough value.

For an initially unsupported AsyncAPI operation, the generated extension contains a compiling placeholder. A later SDK change may intentionally produce a compile error requiring the developer to implement a newly introduced customization hook.

## 4. Publishing remains separately generated

Publishing keeps its established separation: backend service implementations call the producer
interfaces generated by the separately configured `asyncapi-generator` Maven execution.
`@asyncapi` contract DTOs are generated from `asyncapi.yml` by that plugin (through its JSON Schema
or Avro generators), not duplicated as backend domain-event classes. Internal domain events remain
on `EventPublisher`; AsyncAPI events remain on the generated producer contract. Listener generation
does not add a Spring Modulith externalization path or change publishing behavior.

## 5. Referenced `apis {}` models

Every referenced api is loaded lazily-tolerant (`continueOnZdlError` downgrades load failures to
warnings) and parsed **by its declared type**:

- `type: asyncapi` / `openapi` → YAML `$RefParser` via `SpecResourceLoader` (URI-relative `$ref`s).
- `type: zdl` → the ZDL parser (`io.zenwave360.language.zdl.ZdlParser`), producing a separate ZDL
  model map. Referenced ZDLs never load their own `apis {}` references (no recursion), and are
  never merged or concatenated with the primary model.

Relative uris resolve against the document that declares them.

## 6. Cross-module `@listener` contract

`@listener` is repeatable; every occurrence in `optionsList` is one binding. Two forms:

- `@listener(zdl: <ApiName>, event: <Event>)` — cross-module. Resolution: `apis[<ApiName>]` must
  exist with `type: zdl` (hard failure otherwise); the event must exist in the referenced model
  (hard failure); the payload Java type is fully qualified from the **referenced module's layout**:
  `referencedLayout.domainEventsPackage + "." + EventClassName`, where the referenced layout is the
  referenced config's `layout` class (default `DefaultProjectLayout`) processed with the referenced
  config, overridable per api via the api's config body (`layout.domainEventsPackage "..."`).
- `@listener({event: <Event>})` — same-module. The event must exist in the primary model; the type
  resolves in the module's own `domainEventsPackage`.

Listener implementation is controlled independently by `implementEventListeners`. Generation groups bindings **one class per source**: cross-module groups per referenced api
(`<ApiName-minus-Zdl/Api>EventsListener`), same-module groups per owning service
(`<ServiceName>EventsListener`). Internal listener methods always use Spring Modulith's
`@ApplicationModuleListener`; `useSpringModulith` does not enable or disable their implementation.

Per-binding implementation modes:

- `MAPPER` — the service method takes exactly one local bean input: generate the plain mapper contract
  (regenerated) + generated-once MapStruct extension (decision 2) and delegate through it.
- `CUSTOM_REQUIRED` — anything else (ids, pagination, arrays, missing types): compiling
  `UnsupportedOperationException` body with a TODO, in the generated-once class.
